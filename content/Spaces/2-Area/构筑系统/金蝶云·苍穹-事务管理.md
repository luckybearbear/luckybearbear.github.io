# 苍穹平台事务管理

> 金蝶云苍穹平台的事务传播机制与最佳实践

## 核心概念

**事务传播行为**是业务层方法之间互相调用时的事务处理机制。当一个事务方法被另一个事务方法调用时,必须指定事务应该如何传播(例如:继续在现有事务中运行,或开启一个新事务)。

> 事务传播行为是苍穹平台的事务增强特性,并不是事务实际提供方数据库的行为。

---

## 一、五种事务传播类型

### 1.1 SUPPORTS (默认类型)

**传播规则:**
- 如果当前存在一个事务,则支持当前事务
- 如果当前没有事务,就以非事务方式执行
- **这是平台默认的事务传递类型**

**适用场景:**
- 读写操作混合的场景
- 对事务要求不严格的辅助方法
- 日志记录、统计等非核心操作

**示例:**

```java
// 默认使用SUPPORTS
void updateUserInfo(User user) {
    logService.recordLog(user);  // SUPPORTS:跟随外层事务
    userDao.update(user);
}
```

### 1.2 REQUIRED

**传播规则:**
- 如果当前没有事务,就新建一个事务
- 如果已经存在一个事务,加入到这个事务中

**适用场景:**
- 核心业务逻辑
- 必须保证数据一致性的操作
- 需要原子性的多个数据库操作

**示例:**

```java
try (TXHandle h = TX.required("fi_voucher_submit")) {
    // 如果外层没有事务,创建新事务
    // 如果外层有事务,加入外层事务
    voucherDao.save(voucher);
    detailDao.saveDetails(details);
}
```

### 1.3 REQUIRES_NEW

**传播规则:**
- **总是开启一个新的事务**
- 如果当前存在事务,则把当前存在的事务挂起

**适用场景:**
- 需要独立事务的操作
- 无论外层事务成功与否,都必须执行的操作
- 审计日志、历史记录等

**示例:**

```java
void processOrder(Order order) {
    try (TXHandle h = TX.required()) {
        orderDao.save(order);  // 主事务
    }

    // 独立事务,无论主事务成功失败都记录
    try (TXHandle h = TX.requiresNew("order_audit")) {
        auditLogService.log(order);
    }
}
```

### 1.4 NOT_SUPPORTED

**传播规则:**
- **以非事务方式执行操作**
- 如果当前存在事务,就把当前事务挂起

**适用场景:**
- 不需要事务的只读操作
- 报表查询、数据导出
- 大批量数据读取

**示例:**

```java
void exportReport() {
    try (TXHandle h = TX.notSupported()) {
        // 非事务方式执行,避免长事务
        List<Data> data = reportDao.queryAll();
        exportToFile(data);
    }
}
```

### 1.5 NESTED

**传播规则:**
- 如果当前已经存在一个事务,在**嵌套事务**(子事务)中运行
- 子事务出现错误,**不影响其他事务**
- 但**主事务回滚,子事务将一起回滚**
- 如果当前事务不存在,与REQUIRES_NEW一样新起一个事务

**适用场景:**
- 需要部分回滚的场景
- 主流程中可失败的辅助操作
- 复杂业务流程的分阶段提交

**示例:**

```java
try (TXHandle h = TX.required("main_process")) {
    // 主事务操作
    mainDao.save(data);

    // 嵌套事务:可以独立回滚
    try (TXHandle h = TX.nested("sub_process")) {
        secondaryDao.save(detail);
    } catch (Exception e) {
        // 子事务回滚,不影响主事务
    }

    // 主事务继续
}
```

### 1.6 五种传播类型对比

| 类型 | 无事务时 | 有事务时 | 独立性 | 使用频率 |
|------|----------|----------|--------|----------|
| **SUPPORTS** | 非事务执行 | 加入现有事务 | 低 | ⭐⭐⭐⭐⭐ (默认) |
| **REQUIRED** | 创建新事务 | 加入现有事务 | 低 | ⭐⭐⭐⭐ |
| **REQUIRES_NEW** | 创建新事务 | 挂起现有事务,创建新事务 | 高 | ⭐⭐⭐ |
| **NOT_SUPPORTED** | 非事务执行 | 挂起现有事务 | 高 | ⭐⭐ |
| **NESTED** | 创建新事务 | 创建嵌套事务 | 中 | ⭐⭐ |

## 二、TX控制器API

### 2.1 方法签名

**苍穹平台提供的TX接口方法:**

```java
// SUPPORTS类型(默认)
public static TXHandle notSupported()
public static TXHandle notSupported(String tag)

// REQUIRED类型
public static TXHandle required()
public static TXHandle required(String tag)

// REQUIRES_NEW类型
public static TXHandle requiresNew()
public static TXHandle requiresNew(String tag)

// NESTED类型
public static TXHandle nested()
public static TXHandle nested(String tag)
```

**参数说明:**
- `tag`: 事务标签,用于标识和追踪事务
  - 建议使用功能模块名称
  - 例如: `"fi_voucher_submit"` (财务凭证提交)
  - 例如: `"order_create"` (订单创建)

### 2.2 基本用法

**标准使用模式:**

```java
try (TXHandle h = TX.required("business_operation")) {
    try {
        // 业务逻辑代码
        dao.save(entity);
        service.process(data);

    } catch (Throwable e) {
        // 标记回滚
        h.markRollback();
        throw e;
    }
}
```

**关键点:**
1. 使用 **try-with-resources** 确保事务自动关闭
2. 捕获异常后调用 `h.markRollback()` 标记回滚
3. 重新抛出异常让上层处理
4. 无异常时自动提交

### 2.3 快速上手示例

```java
// 示例1: 默认的SUPPORTS
public void updateUser(User user) {
    // 使用默认传播类型
    try (TXHandle h = TX.notSupported()) {
        userDao.update(user);
    }
}

// 示例2: 必须有事务的REQUIRED
public void createOrder(Order order) {
    try (TXHandle h = TX.required("order_create")) {
        orderDao.save(order);
        orderItemService.saveItems(order.getItems());
    }
}

// 示例3: 独立事务的REQUIRES_NEW
public void processWithAudit(Order order) {
    // 主事务
    try (TXHandle h = TX.required("order_process")) {
        orderDao.updateStatus(order);
    }

    // 独立的审计事务
    try (TXHandle h = TX.requiresNew("audit_log")) {
        auditService.log(order);
    }
}
```

## 三、使用注意事项

### 3.1 禁止跨库写 ❌

**规则:**
- 一个事务里,**禁止写两个或以上的物理库**
- DB检测到会抛出异常

**问题示例:**

```java
// ❌ 错误:跨库写
try (TXHandle h = TX.required()) {
    db1Dao.save(data1);  // 写入物理库1
    db2Dao.save(data2);  // 写入物理库2 - 抛出异常!
}
```

**原因:**
- 分布式事务的复杂性
- 跨库事务性能差
- 数据一致性难以保证

### 3.2 禁止跨微服务节点事务 ❌

**规则:**
- 跨微服务节点的事务在API调用时将被检测并抛异常

**场景1: 微服务A调用微服务B**

```shell
微服务A (有事务) → API调用 → 微服务B (不可有事务)
```

```java
// 微服务A
try (TXHandle h = TX.required()) {
    localService.save(data);
    remoteServiceB.process(data);  // B中不可有事务
}
```

**场景2: 微服务A → 微服务B → 微服务C**

```shell
微服务A (有事务)
    → API调用 → 微服务B (不可有事务)
        → API调用 → 微服务C (不可有事务)
```

**原因:**
- 微服务独立部署,物理分离
- 跨服务事务难以实现和保证
- 避免分布式事务的复杂性

**正确做法:**
- 微服务间使用**最终一致性**
- 采用**MQ异步调用**
- 使用**Saga模式**或**TCC模式**

### 3.3 避免大事务 ❌

**问题:**
- 大事务执行效率低
- 造成其他事务长时间**锁等待**和**锁冲突**
- 容易发生**阻塞**或者**死锁**

**大事务的典型特征:**
- 事务执行时间过长(>3秒)
- 事务中包含大量数据库操作
- 事务中调用外部服务
- 事务中包含复杂计算

**问题示例:**

```java
// ❌ 错误:大事务
try (TXHandle h = TX.required()) {
    // 1. 查询大量数据
    List<Data> dataList = dao.findAll();

    // 2. 复杂计算
    for (Data data : dataList) {
        processData(data);  // 耗时操作
    }

    // 3. 批量保存
    for (Data data : dataList) {
        dao.update(data);
    }

    // 4. 调用外部服务
    externalService.notify(dataList);
}
// 可能执行几十秒甚至更长时间!
```

## 四、解决方案与最佳实践

### 4.1 跨库写的解决方案

**方案1: 使用MQ异步调用**
- 适用场景:只有正向操作
- 例如:订单创建后异步通知库存系统

```java
// 订单服务
try (TXHandle h = TX.required("order_create")) {
    orderDao.save(order);
    mqService.send("inventory.update", order);
}

// 库存服务
@MQListener("inventory.update")
public void updateInventory(Order order) {
    try (TXHandle h = TX.required("inventory_update")) {
        // 独立事务更新库存
        inventoryDao.update(order);
    }
}
```

**方案2: 设计成业务流程**
- 适用场景:要支持反向操作
- 使用工作流引擎或状态机
- 将跨库操作分解为多个步骤

### 4.2 跨微服务事务的解决方案

**推荐方案:**

1. **MQ异步调用**(最常用)

   ```java
   // 服务A:主流程
   public void processOrder(Order order) {
       try (TXHandle h = TX.required("order_create")) {
           orderDao.save(order);
           // 发送MQ消息,异步处理
           mqProducer.send("order.created", order);
       }
   }

   // 服务B:消费消息
   @MQListener("order.created")
   public void handleOrderCreated(Order order) {
       try (TXHandle h = TX.required("inventory_update")) {
           inventoryService.deduct(order);
       }
   }
   ```

2. **Saga模式**(长事务)
   - 定义一系列本地事务
   - 每个本地事务都有对应的补偿事务
   - 失败时执行补偿操作

3. **TCC模式**(Try-Confirm-Cancel)
   - Try:资源预留
   - Confirm:确认执行
   - Cancel:取消执行

### 4.3 大事务的拆分

**拆分策略:**

1. **识别耗时操作**
   - 外部服务调用
   - 复杂计算
   - 大量数据操作

2. **拆分为多个小事务**

   ```java
   // ❌ 大事务
   try (TXHandle h = TX.required()) {
       validate();      // 验证
       calculate();     // 计算
       saveMain();      // 保存主数据
       saveDetail();    // 保存明细
       sendNotify();    // 发送通知
   }

   // ✅ 拆分后
   // 事务1: 验证和计算
   try (TXHandle h = TX.required("validate")) {
       validate();
       calculate();
   }

   // 事务2: 保存数据
   try (TXHandle h = TX.required("save_data")) {
       saveMain();
       saveDetail();
   }

   // 事务3: 异步通知
   try (TXHandle h = TX.requiresNew("notify")) {
       sendNotify();
   }
   ```

3. **使用异步处理**

   ```java
   // 主事务:只保存核心数据
   try (TXHandle h = TX.required("order_create")) {
       orderDao.save(order);
   }

   // 异步:非核心操作
   asyncService.execute(() -> {
       try (TXHandle h = TX.required("async_process")) {
           statisticsService.update(order);
           notificationService.send(order);
       }
   });
   ```

## 五、最佳实践清单

### 5.1 事务使用原则

**✅ 应该做的:**
1. **明确事务边界**: 清晰定义事务的开始和结束
2. **选择正确的传播类型**: 根据业务需求选择
3. **事务尽可能短**: 减少锁持有时间
4. **使用有意义的tag**: 便于追踪和调试
5. **正确处理异常**: 使用`markRollback()`

**❌ 不应该做的:**
1. **跨库写**: 一个事务写多个物理库
2. **跨微服务事务**: API调用链上的事务
3. **大事务**: 长时间运行的事务
4. **在循环中创建事务**: 应该批量处理
5. **忽略异常处理**: 不使用`markRollback()`

### 5.2 代码审查检查点

**事务相关审查项:**
- [ ] 是否使用了正确的传播类型?
- [ ] 是否存在跨库写操作?
- [ ] 是否存在跨微服务事务?
- [ ] 事务执行时间是否过长(>3秒)?
- [ ] 是否在循环中创建事务?
- [ ] 异常处理是否正确?
- [ ] 事务tag是否有意义?

### 5.3 性能优化建议

**优化事务性能:**
1. **减少事务范围**: 只包含必要的操作
2. **使用批量操作**: 减少数据库交互次数
3. **避免在事务中调用外部服务**: 外部服务响应时间不可控
4. **合理使用索引**: 减少锁等待
5. **使用读写分离**: 查询操作使用NOT_SUPPORTED
6. **异步处理非核心操作**: 统计、日志、通知等

## 六、常见问题

### 6.1 如何选择传播类型?

**决策树:**

```shell
需要事务吗?
├─ 不需要 → NOT_SUPPORTED
└─ 需要
    ├─ 必须独立运行吗?
    │   ├─ 是 → REQUIRES_NEW
    │   └─ 否 → 继续判断
    ├─ 需要嵌套事务吗?
    │   ├─ 是 → NESTED
    │   └─ 否 → 继续判断
    └─ 是否有外层事务?
        ├─ 不确定/无所谓 → SUPPORTS (默认)
        └─ 必须有事务 → REQUIRED
```

### 6.2 事务标签(tag)如何命名?

**推荐命名规范:**

```shell
{模块}_{功能}_{操作}

示例:
- fi_voucher_submit (财务_凭证_提交)
- order_create (订单_创建)
- inventory_update (库存_更新)
- user_profile_update (用户_个人资料_更新)
```

### 6.3 如何调试事务问题?

**调试方法:**
1. **查看日志**: 搜索事务tag
2. **监控工具**: 使用苍穹Monitor
3. **数据库监控**: 查看锁等待情况
4. **分布式追踪**: 使用链路追踪工具

## 七、与Spring事务的对比

### 7.1 传播类型对应关系

| 苍穹 | Spring | 说明 |
|------|--------|------|
| SUPPORTS | SUPPORTS | 相同 |
| REQUIRED | REQUIRED | 相同 |
| REQUIRES_NEW | REQUIRES_NEW | 相同 |
| NOT_SUPPORTED | NOT_SUPPORTED | 相同 |
| NESTED | NESTED | 相同(实现不同) |

### 7.2 使用方式对比

**Spring事务:**

```java
@Transactional(propagation = Propagation.REQUIRED)
public void method() {
    // 业务逻辑
}
```

**苍穹事务:**

```java
try (TXHandle h = TX.required("tag")) {
    // 业务逻辑
}
```

**差异:**
- Spring使用注解声明式
- 苍穹使用编程式API
- 苍穹更显式,更易控制

## 八、总结

### 8.1 核心要点

1. **五种传播类型**: SUPPORTS(默认)、REQUIRED、REQUIRES_NEW、NOT_SUPPORTED、NESTED
2. **三大禁止**: 禁止跨库写、禁止跨微服务事务、避免大事务
3. **解决方案**: MQ异步、业务流程设计、事务拆分
4. **最佳实践**: 明确边界、短事务、正确处理异常

### 8.2 记住这几点

> **金蝶苍穹事务管理三原则:**
> 1. **一个事务一个库**
> 2. **跨服务不用事务**
> 3. **事务越短越好**
